# Технический аудит Naza Couture

**Дата аудита:** 10 ноября 2026 г.

**Область:** статический сайт в корне репозитория и `ua/`, связанные ресурсы и конфигурационные файлы репозитория.

**Режим:** чтение. Исходники проекта не редактировались; этот отчёт создан по запросу.

## 1. Краткий вывод

- Сайт — набор статических HTML-страниц, без CMS, package manifest, сборщика, серверного кода или контентной JS-модели. Основные данные находятся непосредственно в HTML, а не в [`js/scripts.js`](./js/scripts.js).
- Основной контент в двух языках расположен в отдельных страницах. Прайс-листы имеют одинаковые числовые значения, но переведённые наименования; расписание продублировано на главных и контактных страницах обоих языков.
- В текстовых узлах страниц не обнаружены объявления, уведомления о временном закрытии или явно указанные выходные. В расписании показаны понедельник–суббота; отсутствие воскресенья не пояснено отдельным текстом «закрыто».
- Активное портфолио строится из шести работ в HTML. Для каждой работы карточка и модальное окно дублируют ссылку на изображение; порядок карточек задаётся порядком DOM.
- В `img/` находится отдельный архив изображений/видео, на который страницы не ссылаются. Активные изображения сайта лежат преимущественно в `assets/img/`.
- Страницы и sitemap содержат канонические URL домена GitHub Pages `binehold-coder.github.io/naza`, а ссылки в футере ведут на корневой `/legal.html`. Последняя ссылка работает на домене с корнем сайта в `/`, но при публикации как GitHub Pages project site путь может обходить `/naza/`. В репозитории нет Vercel-конфигурации или workflow, поэтому связь репозитория с конкретным Vercel-проектом по исходникам не подтверждается.

## 5. Внутренние ссылки, внешние зависимости и деплой

### Внутренние переходы

- Navbar связывает главную, услуги, портфолио, «О нас» и контакты. Ссылки между FR и UA в соответствующих страницах ведут на эквивалентные страницы.
- Карточки портфолио открывают модальные окна на той же странице через `#portfolioModal1`–`#portfolioModal6`.
- Страница 404 содержит ссылки на корневую главную и UA главную.
- Локальные пути к CSS, JS, изображениям и HTML-страницам разрешаются в дереве репозитория при проверке относительных файловых ссылок.
- Footer всех страниц использует `href="/legal.html"`. Абсолютный путь от доменного корня подходит для custom domain/Vercel с корнем сайта `/`, но не для текущего GitHub Pages project URL с префиксом `/naza`; в таком окружении ссылка может уйти на `/<legal.html>` вне проекта.
- У [`legal.html`](./legal.html) есть переключатель UA на украинскую главную, а не на перевод legal-страницы, поскольку отдельной украинской legal-страницы нет.

### Внешние библиотеки и сервисы

- Font Awesome 6.3.0 загружается с `use.fontawesome.com`.
- Bootstrap 5.2.3 JavaScript bundle загружается с jsDelivr; он используется для мобильного navbar и модальных окон портфолио.
- Шрифты Montserrat и Roboto Slab загружаются с Google Fonts.
- Google Maps отображается iframe на главной и контактной страницах обоих языков. Встроенный URL содержит наименование ателье, геокоординаты и французский интерфейс `hl=fr`.
- Instagram и Facebook — внешние ссылки в контактных блоках и футерах; ссылки открываются в новой вкладке с `rel="noopener noreferrer"`.
- Форм обратной связи или клиентских форм в просмотренных страницах нет. На legal-странице указано, что сайт не использует cookies и не собирает данные через формы.
- [`js/scripts.js`](./js/scripts.js) использует глобальный `bootstrap` из CDN и не хранит клиентский контент.

### Развёртывание

На момент аудита в исходниках `canonical`, OG URL, `robots.txt` и `sitemap.xml` указывают на `https://binehold-coder.github.io/naza/`. В корне не обнаружены `vercel.json`, `package.json`, конфигурация сборщика или `.github/workflows/`. Это не доказывает отсутствие внешних настроек в GitHub/Vercel, но в репозитории нет проверяемой автоматизации деплоя. Перед переключением на Vercel следует синхронизировать canonical/OG URL, robots/sitemap и пути к страницам с фактическим production-доменом и выбранным base path.

## 7. Рекомендация: управление через Telegram без CMS

### Предлагаемый поток

1. **Хранить редактируемые данные отдельно от HTML.** Перенести расписание, контакты, объявления, прайс и список работ в JSON/YAML-файлы репозитория, например `content/site.json`, `content/services.json` и `content/portfolio.json`. Для текстового контента использовать поля `fr` и `uk`; для цен — одно общее числовое значение/текст цены, чтобы избежать расхождений переводов. Для portfolio хранить `image`, `alt.fr`, `alt.uk`, `title.fr/uk`, `description.fr/uk`, `order`, `visible`.
2. **Оставить сайт статическим.** Добавить небольшой build script, который проверяет схему контента и генерирует текущие HTML-файлы либо собирает их из шаблонов. Предпочтителен HTML, сгенерированный при сборке, а не загрузка JSON на клиенте: это сохраняет SEO/социальные метаданные и не требует динамического backend на страницах сайта.
3. **Бот принимает только разрешённые команды.** Telegram webhook на защищённом серверном endpoint (например, отдельной serverless-функции) с проверкой Telegram webhook secret, allowlist `chat_id`/пользователей и типизированными командами: изменить цену, часы, объявление с датой начала/окончания, добавить/скрыть/переместить работу. Не принимать произвольный HTML, shell-команды, имена файлов или произвольные git-команды.
4. **Изображения загружать контролируемо.** Ограничить тип/размер файла, генерировать безопасное имя, проверить формат и сохранить в `assets/img/portfolio/`; метаданные работы записать в JSON. Не использовать исходное имя пользователя как путь.
5. **Публиковать через GitHub PR.** Бот проверяет схему и создаёт отдельную ветку с изменением только нужного JSON/файла изображения, затем открывает PR с превью и diff для подтверждения владельцем. Токен GitHub App с минимальными разрешениями хранить только в secret store серверного окружения; не помещать его в сайт или репозиторий. Прямой push в production допустим только после отдельного решения; PR даёт откат и контроль ошибок.
6. **Автоматическая проверка и деплой.** GitHub Actions при PR выполняет JSON/schema validation, проверяет существование картинок, уникальность ID/порядка и обязательные переводы, запускает HTML/link checks и сборку. Подключённый к production-ветке Vercel создаёт preview deployment для PR и production deployment после merge. Секреты Vercel/GitHub/Telegram задаются в настройках провайдеров, не в исходниках.
7. **Аудит и безопасность операций.** Ограничить права Telegram-команд по пользователю, хранить журнал действия (кто/что/время/PR), подтверждать опасные действия вроде удаления или публикации без ревью. При ошибке сборки/деплоя бот сообщает статус, не заявляя об успешной публикации.

### Почему не править HTML напрямую ботом

Сейчас одинаковые данные копируются по нескольким страницам, языковые версии уже частично расходятся, а карточка портфолио имеет связанный modal ID и повтор изображения. Прямой поиск/замена строк может изменить не все вхождения или нарушить HTML-связи. Единый контентный источник с генерацией страниц позволяет менять цену один раз, переводы по отдельным полям, а порядок работ — одним массивом с автоматическим рендером обеих языковых версий.
